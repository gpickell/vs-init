This Windows machine is set up to manage a VertiGIS Studio deployment that actually runs somewhere else: a separate Linux server, using Docker. You don't need to become a Linux person to use it -- this page explains the handful of concepts that matter and what each button in this extension actually does.

What you're looking at

This VS Code window is connected directly to that Linux server over SSH (that's what "Remote (SSH)" in the bottom-left corner means). When you open or edit a file here, you're editing the real file on the server, immediately -- there's no separate upload step, no syncing. Closing this window doesn't undo anything you've already saved.

Everything lives under one folder on that server: /opt/vertigis-studio. That's the folder this window has open.

Projects and compose.yml

Inside /opt/vertigis-studio, each subfolder is a project -- one self-contained thing that Docker runs. You'll typically have:

  • A caddy project (named caddy or caddy-1) -- the "front door." It's what actually receives web traffic from the internet/your network and forwards it to the right place, and it's what handles HTTPS.
  • One or more studio projects (studio-1, studio-2, ...) -- each one is a running copy of VertiGIS Studio itself.

Every project has a compose.yml file -- that's the file that tells Docker what to run and how to configure it. You don't need to understand Docker Compose as a format to use this extension; just know that:

  • A line like environment: introduces a list of settings, one per line below it, each shaped like SETTING_NAME: value. Changing the deployment's behavior almost always just means changing the text after one of these colons.
  • A line starting with # is a comment -- a note for humans, Docker ignores it. Some of those comments are what make the buttons described below show up.

The side panel

Open it from the VertiGIS Studio icon in the Activity Bar (the strip of icons on the far left). It has:

  • Add Caddy / Add Studio -- create a new project folder with a ready-to-edit compose.yml already in it.
  • Compose Projects -- every existing project, as a clickable list that jumps straight to its compose.yml.
  • Guidance -- brings you back to this page any time.

The buttons that appear inside compose.yml

Open any project's compose.yml and you'll see small clickable links (VS Code calls these "CodeLens") floating just above certain lines. Each one runs a real action -- most of them open a terminal-like panel at the bottom (named vs-init) so you can watch what's happening; that panel is reused for whatever you click most recently, not one per action.

Appears above: the environment: line, for a studio project

Get Account ID

Opens your web browser so you can sign in and confirm which VertiGIS Studio account this deployment belongs to. Fills in VERTIGIS_ACCOUNT_ID for you -- you never have to go look that value up yourself.

Appears above: the environment: line, for a studio project

Register App / Update App

Your organization's ArcGIS/Portal sign-in needs to know about this specific deployment before users can log into it. Clicking this opens a browser window for you to sign in to your portal, then registers (or updates) an application entry there automatically and fills in ARCGIS_APP_ID. Register App always stays available even after you've already registered once -- clicking it again just creates a fresh registration, which is sometimes exactly what you want (e.g. starting over cleanly); Update App only appears once there's already an app id, and just refreshes its settings instead of creating a new one.

Appears above: the environment: line, for a studio project

Request Cert / Retrieve Cert

If your organization has its own internal certificate authority (common for anything not meant to be public on the internet), this requests a real HTTPS certificate for this deployment's web address from it, using your Windows machine's own certificate tools -- you may see an administrator-approval prompt, since issuing a certificate needs that. Some certificate authorities issue immediately; others take a moment to approve the request first. If Request Cert reports the certificate isn't ready yet, run Retrieve Cert afterward (any time) to pick it up once it is -- re-running either one is always safe.

Appears above: the environment: line, for a studio project

Register CNAME

Tries to automatically point your organization's internal DNS at this server, so people can actually reach this deployment by name. This is best-effort by design: it only works if your network's DNS is set up in a fairly standard way, and it will clearly tell you if it couldn't figure out where to make the change rather than guessing. If it doesn't work, that's expected for some networks -- ask whoever manages DNS at your organization to point the name at this server manually instead.

Appears above: the top of the file, for a studio project (it's file-wide, like Build Caddyfile, not tied to one specific line)

Transfer Enterprise Trust Anchors

If your organization uses its own internal certificate authority (see Request Cert above), the Linux server also needs to be told to trust it -- otherwise it won't trust its own certificate, or anything else signed by your organization. This copies your Windows machine's own list of trusted certificates to the server. Safe to re-run any time (e.g. after your IT department rolls out a new certificate authority).

Appears above: the top of the file, for any project with "# caddy" cues (including the caddy project's own compose.yml)

Build Caddyfile

Looks across every project for two specific comments -- # caddy route url and # caddy route target -- and wires them all together into the caddy project's own configuration, so the front door actually knows how to reach each studio deployment. Run this again any time you add a new studio project or change a web address. It also automatically picks up a real certificate for a deployment (see Request Cert above) if one exists -- nothing to configure separately for that.

Appears above: any image: line

Pick Version

Shows every real released version of that image (VertiGIS Studio, or Caddy) actually available right now, newest first, and lets you pin this project to a specific one instead of always using latest. Useful when you want this deployment to stop moving until you deliberately decide to upgrade it.

The certs folder

The certs folder visible in the Explorer (alongside your project folders) is normally managed for you by the buttons above. If you already have certificate material from somewhere else -- an existing enterprise certificate, or a CA your organization manages outside this tool -- you can put it in place yourself instead of using Request Cert or Transfer Enterprise Trust Anchors:

  • certs/root/ -- trusted root/intermediate CA certificates, one .pem file each. This whole folder becomes every container's trusted certificate list. Adding a .pem file here yourself isn't enough on its own -- run Transfer Enterprise Trust Anchors again afterward (it re-indexes the whole folder, including anything you added by hand) so it actually gets trusted.
  • certs/live/<host>/ -- one folder per web address, containing fullchain.pem and privkey.pem for that host's real serving certificate (exact filenames matter). If you already have a certificate for a host, create this folder and these two files yourself -- Build Caddyfile picks it up automatically next time it runs, no need to involve Request Cert at all.
  • certs/requests/<host>/ -- working files for Request Cert/Retrieve Cert's own process. Not meant to be populated by hand.

Setting up a new deployment, roughly in order

  1. If there's no caddy project yet, click Add Caddy.
  2. Click Add Studio to create a new studio project.
  3. Open its compose.yml and fill in ARCGIS_PORTAL_URL and the # caddy route url/FRONTEND_URL value (the web address people will actually use to reach it).
  4. Click Get Account ID, then Register App.
  5. If your organization uses an internal certificate authority: click Transfer Enterprise Trust Anchors once per server, then Request Cert for this deployment (and Retrieve Cert later if needed).
  6. Click Build Caddyfile to wire the front door up to this deployment.
  7. Optionally, click Register CNAME to try to point DNS here automatically.
  8. Start the containers. Two equivalent ways to do this:
    • Open the project's compose.yml and look for Run Services just above the services: line -- that's a CodeLens from the Container Tools extension already installed in this window, not one of vs-init's own buttons.
    • Or the same steps from a shell instead: right-click the project's folder in the Explorer and choose Open in Integrated Terminal (lands you in the right folder automatically), or bring up any terminal via Terminal > New Terminal (or Ctrl+`) and cd into the project's folder yourself -- then run docker compose up -d.
